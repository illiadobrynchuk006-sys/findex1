# Лабораторна робота №1 — Ітератори, генератори та текстовий корпус

**Курс:** Python — Build a Search Engine (`findex`)  
**Тема:** Streams, Not Lists: Iterators, Generators, and Your Corpus  
**Мета:** побудувати початковий модуль пошукової системи: читати корпус по одному документу, перетворювати текст на токени та обчислювати статистику без завантаження всього корпусу в оперативну пам'ять.

## 1. Обраний корпус

Для первинної демонстрації створюється **синтетичний україно-англійський навчальний корпус** із 1000 файлів `.txt` (генератор у `scripts/generate_demo_corpus.py`). Тексти присвячені Python, Unicode, індексуванню та пошуку. Це **лише тестові дані**, не справжня колекція статей, книг чи особистих нотаток. Для повноцінного продовження курсу обраний напрямок — **відкриті тексти Project Gutenberg**: https://www.gutenberg.org/ebooks/search/?sort_order=downloads. Завантажені з дозволених джерел `.txt` книги потрібно розмістити у `data/books/` (кожна книга — окремий документ). Усі дані в `data/` виключені з Git.

Створення тестового корпусу:

```bash
python scripts/generate_demo_corpus.py
```

Для власних файлів покладіть UTF-8 `.txt` у папку `data/` або її підкаталоги (можна відразу запускати на `data/books/`). Корпус може мати понад 1000 документів; пам'ять не повинна зростати пропорційно загальному обсягу текстів. Зауваження: розмір одного документа все одно впливає на використання пам'яті.

## 4. Як працюють модулі

**`iter_documents(root)`** — генератор. `pathlib.Path.rglob('*.txt')` обходить дерево каталогів, а файл відкривається тільки на поточній ітерації. Кожен результат — `Document(doc_id, path, text)`. Вміст файлу читається в один рядок, тобто в пам'яті є один поточний документ, а не весь корпус. Пошкоджені UTF-8 байти замінюються символом U+FFFD, про що повідомляє лог. Файли, які неможливо прочитати через `OSError`, пропускаються з попередженням.

**`tokenize(text)`** — генератор. Спершу робить `unicodedata.normalize('NFC', text)`, потім `casefold()`, далі видає токени за допомогою `re.finditer` (без проміжного списку збігів).

Правила токенізації:

- **Апостроф:** ASCII `'` та типографський `’` дозволені **всередині** токена: `don't`, `п'ять`, `п’ять`. Два варіанти апострофа залишаються різними токенами (свідома політика).
- **Дефіс:** роздільник: `веб-пошук` → `веб`, `пошук`.
- **Цифри:** зберігаються; `python3` — один токен, `12.5` → `12`, `5`.
- **Підкреслення:** роздільник: `hello_world` → `hello`, `world`.
- **Unicode:** працює з кирилицею; NFC робить `cafe\u0301` еквівалентним `café`.

**`stats.py`** — один прохід через документи. Підраховує число документів, токенів, унікальних термінів та топ-50 слів через `Counter`. Заміряє виконання через `time.perf_counter()` і пік відстежуваних Python-виділень пам'яті через `tracemalloc`. Це **не загальна RAM/RSS процесу**.

## 5. Реальні вимірювання

Замір виконано на одному і тому самому **синтетичному** корпусі, перші 120 документів (`--limit 120`), у середовищі Python 3.13.5. Це показники конкретного виконання, а не універсальні характеристики будь-якого комп'ютера. Кожен режим обчислив **173 760 токенів, 185 унікальних токенів**.

| Версія | Документів | Пік пам'яті, MiB (tracemalloc) | Час, с |
|---|---:|---:|---:|
| eager (списки) | 120 | 14.324 | 0.833 |
| lazy (генератори) | 120 | 0.773 | 0.805 |

**Пояснення:** eager одразу створює список усіх документів, а потім список списків усіх токенів. Тексти та всі проміжні рядки-токени зберігаються одночасно, тому пік значно більший. Lazy бере один документ, по черзі генерує його токени й одразу збільшує частоту в `Counter`, не накопичуючи проміжні списки. Проте пам'ять не нульова: залишаються поточний документ, нормалізований текст, службові об'єкти генераторів і словник частот. Часи близькі, а різниця у пам'яті на цьому зразку суттєва. На справжньому корпусі цифри будуть іншими; після заміни корпусу вимірювання слід повторити.

Для нового заміру скористайтеся командами вище і впишіть отримані цифри у цю таблицю.

## 7. Reflection: відповіді до захисту

1. **Iterable / iterator.** `for` викликає `iter(xs)`, потім `next(it)` до `StopIteration`. Iterable вміє видати ітератор; iterator тримає стан поточної позиції. Генератор є ітератором.
2. **Чому генератор одноразовий?** Після завершення він вичерпаний. Щоб почати заново, треба знову викликати функцію генератора `iter_documents(root)`.
3. **Що в пам'яті на 10 000-му токені?** Один поточний документ, його нормалізований текст, генератор, лічильники та `Counter`, який зберігає частоти вже побачених унікальних слів.
4. **Коли виникає помилка в генераторі?** Під час наступного `next()` (або циклу `for`), а не під час виклику функції, оскільки виконання тіла відкладене до споживання значення.
5. **Навіщо `casefold()` та NFC?** `Straße` і `STRASSE` після `casefold()` збігаються як `strasse`; `lower()` не дає такого самого результату. NFC зводить `cafe\u0301` та `café` до однакової форми.
6. **`findall` проти `finditer`.** `findall` будує список усіх збігів одразу, а `finditer` надає їх по одному, що зменшує проміжне споживання пам'яті.
7. **Чому lazy дешевший за eager?** Eager зберігає всі тексти й списки токенів одночасно. Lazy зберігає тільки поточний документ, текст після нормалізації та таблицю частот. Пікова пам'ять від цього менша, але не нульова.

# Лабораторна №2 — Інвертований індекс

Лабораторна №2 продовжує той самий корпус і токенізатор із лабораторної №1.

## Запуск

```bash
python -m pip install -e ".[dev]"
python scripts/generate_demo_corpus.py
python -m findex.index data/demo/ --out index.bin
python -m findex.search index.bin "пошук AND обробка"

python -m findex.search index.pkl "пошук NOT python" --format pickle
python scripts/benchmark_lab02.py data/demo/

```

## Реалізація

- `src/findex/index.py`: словник термінів, відсортовані за `doc_id` постинги `(doc_id, tf)`, довжини документів і шляхи.
- `DocMeta` — незмінюваний `@dataclass(frozen=True, slots=True)`.
- `src/findex/search.py`: запити AND/OR/NOT через два вказівники (merge) або множини (set); оператори обчислюються **зліва направо**; дужки не підтримуються.
- Зберігання: pickle (лише для власних довірених файлів!) та бінарний формат із заголовком `FIDX02`, uint32 довжиною й UTF-8 JSON-даними.
- Компактна альтернатива: `array('I')` з парами порядковий номер документа / частота та зовнішнім відображенням номерів на ID.
- `tests/test_index_search.py` перевіряє індексацію, пошук, серіалізацію та помилки.

## Reflection

1. **Чому відсортовані постинги?** Два вказівники виконують перетин/об'єднання за лінійний час O(n+m) без хеш-таблиць на кожен запит.
2. **Навіщо defaultdict і Counter?** Легко додавати списки постингів та рахувати частоти за один прохід документа.
3. **Чому slots економить пам'ять?** Уникає окремого словника атрибутів об'єкта; array компактно пакує цілі числа, але потребує таблиці номерів документів.
4. **Чому pickle небезпечний?** Завантаження недовіреного pickle може виконати чужий код.
5. **Merge vs set.** Merge працює з готовими відсортованими списками; set створює додаткові хеш-таблиці, які іноді пришвидшують операції ціною пам'яті.

# Лабораторна №3 — Рейтинг і модель об'єктів

## Нові компоненти

- `src/findex/model.py`: клас `Index` реалізує `collections.abc.Mapping`: `len(index)`, `term in index`, `index[term]`, ітерацію, `repr`, `num_docs`, `df(term)`, `avg_doc_length` через `cached_property`. Менеджер контексту `with open_index(path) as index:`.
- `src/findex/query.py`: рекурсивний спуск для `AND`, `OR`, `NOT`, дужок та фраз у лапках. Пріоритет: `NOT > AND > OR`. AST: `Term`, `Phrase`, `And`, `Or`, `Not`, обчислення через `evaluate(index)` (у реалізації: `evaluate(ast, index)`).
- `src/findex/rank.py`: `Scorer` з TF-IDF та BM25 (`k1=1.5`, `b=0.75`), `heapq.nlargest`, `SearchResult(order=True)`, `@timed` із `functools.wraps`, кеш за трійкою (query, method, top_k), контекстні сніпети.
- `scripts/evaluate_lab03.py`: P@5 за 10 вручну розміченими запитами.
- `tests/test_lab03.py`: тести моделі, AST, фраз, пошуку, кешу і рейтингу.

**Особливості реалізації:** фразовий пошук перевіряє сусідні токени повторним читанням вихідних текстів, а не позиційними постингами. Для великого корпусу це повільніше. `open_index()` створює індекс із папки і очищає власні структури після виходу з `with`. Старі CLI лабораторій 1–2 не змінено.

## Запуск у GitHub Codespaces

```bash
git switch main
git pull origin main
python -m pip install -e .
python scripts/generate_demo_corpus.py
python -m findex.rank data/demo/ "python AND (пошук OR документ)" --method bm25 --top 5
python -m findex.rank data/demo/ '"потокове читання"' --method tfidf --top 5
python -m pytest
```

## Санітарні перевірки рейтингу

1. **Рідкісний термін важить більше частого:** у TF-IDF і BM25 IDF зростає, коли `df` зменшується (за інших однакових умов).
2. **Повторення терміна має спадну віддачу:** у TF-IDF використовується `1+log(tf)`, у BM25 є насичення частоти.
3. **Короткий документ із одним входженням може обійти довгий:** у BM25 використовується нормалізація за довжиною документа. Результат залежить і від інших термінів запиту.

## Precision@5

Створіть власний `judgments.json` з рівно 10 об'єктів `{"query":"...", "relevant":["doc_id1", "doc_id2"]}`, де `relevant` — **вручну перевірені** релевантні документи, і запустіть:

```bash
python scripts/evaluate_lab03.py data/demo/ judgments.json
```

| Запит | TF-IDF P@5 | BM25 P@5 |
|---|---:|---:|
| 1–10 | заповнити після ручної розмітки | заповнити після ручної розмітки |

**P@5** = число релевантних у перших 5 результатах / 5. Дані ручної розмітки не вигадуються. Десять оцінок треба отримати на власному корпусі.

## Декоратор і кеш

`@timed` обгортає виклик пошуку й пише час у лог незалежно від винятку, а `@wraps` зберігає ім'я та метадані функції. Кеш `Scorer` працює у межах одного об'єкта під час одного процесу; повторіть той самий `scorer.search(query)` двічі — другий раз `cache_hits` зросте.

## Reflection

- **Навіщо dunder-методи?** `Index` використовують як звичайну колекцію Python (`len`, `in`, `[]`, `for`) через протокол `Mapping`.
- **Чому BM25?** Він коригує внесок терміна за частотою, рідкісністю та довжиною документа.
- **Навіщо AST?** Вираз `python AND (async OR await) NOT java` має вкладену структуру, яку не можна коректно обробити простим `split()`.
- **Обмеження:** для цитованих фраз зараз потрібно мати вихідні файли корпусу; позиційні постинги можна додати у наступній версії.

## Здача

Після запуску тестів, демонстрації пошуку й заповнення таблиці ручної оцінки зробіть тег `lab-03` із поточного `main`. Попередні теги `lab-01` і `lab-02` лишаються незмінними.

## Reflection

- **Навіщо Protocol?** Дозволяє передавати різні реалізації з однаковими методами без спадкування.
- **Навіщо strict pyright?** Виявляє неоднозначні типи, некоректні контракти та потенційні помилки до запуску.
- **Чому property-based testing?** Hypothesis перевіряє інваріанти на багатьох автоматично генерованих прикладах.
- **Чому `--json`?** Стандартизований вивід можна обробляти іншими програмами без парсингу оформлених таблиць.
- **Чому wheel?** Встановлюваний пакет можна запускати з будь-якої робочої директорії.

**Поточні відкриті вимоги:** повний strict typecheck, Protocol для Scorer та властивості серіалізації/постингів, coverage, CI badge, підтверджена збірка wheel і GitHub Release.

# Лабораторна №5 — Конкурентність і GIL

Додано `src/findex/parallel.py` (модульний воркер `build_partial`, детерміноване `merge`,

Шляхи передаються воркерам замість прочитаних документів. Для процесів використовується
`multiprocessing.get_context("spawn")`, а помилки `executor.map` передаються викликачу.

## Демонстрація

```bash
git switch main
git pull origin main
python -m pip install -e .
python -m pip install pytest matplotlib psutil
python scripts/generate_demo_corpus.py
findex index data/demo --out serial.bin --workers 1 --executor serial
findex index data/demo --out threads.bin --workers 4 --executor threads
findex index data/demo --out processes.bin --workers 4 --executor processes
python -m pytest tests/test_parallel_lab05.py
python scripts/benchmark_lab05.py data/demo --repeats 3
```

Бенчмарк створить `benchmarks/lab05/measurements.csv` та `speedup.png`.
Після запуску додайте фактичні результати й графік у GitHub, підставте дані в таблицю нижче.
Мінімум три повтори на кожну конфігурацію (медіани).
`serial/1` використовується як база для прискорення.
`os.cpu_count()` визначає додаткову точку з кількістю логічних CPU.

| Executor | Workers | Wall, s | CPU, s | RSS, KiB | Speedup |
|---|---:|---:|---:|---:|---:|
| serial | 1,2,4,8,cpu_count | запустити | запустити | запустити | запустити |
| threads | 1,2,4,8,cpu_count | запустити | запустити | запустити | запустити |
| processes | 1,2,4,8,cpu_count | запустити | запустити | запустити | запустити |

**Метрики Linux:** CPU — витрачений час процесора батьківського та завершених дочірніх
процесів через `resource.getrusage`; RSS — максимум із high-water marks батьківського
і найбільшого дочірнього процесу (KiB), **не сумарний одночасний RSS групи**.
Для сукупного RSS потрібен окремий профайлер групи процесів. Виміри на користувацькому корпусі
поки що не виконані.

## GIL — пояснення

- За звичайного CPython із GIL потоки не виконують Python bytecode CPU-bound
  паралельно; тому індексація з активною токенізацією може не прискоритися.
- Процеси мають окремі інтерпретатори й можуть працювати на кількох ядрах,
  але запуск, серіалізація даних та об'єднання постингів додають накладні витрати.
- Для операцій очікування I/O потоки часто доречніші.
- Закон Амдала: якщо частка роботи залишається послідовною, прискорення має межу.
- Збірка CPython 3.13 free-threaded без GIL (опційний експеримент) перевіряється
  через `sys._is_gil_enabled()`, якщо метод доступний.
